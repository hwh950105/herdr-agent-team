# 유지보수 절차 (기존 코드의 기능 수정·추가)

이미 있는 프로젝트에서 기능을 고치거나 더할 때 Claude가 따르는 절차다. 역할·소유 경계·보고·안전 규칙은 `AGENTS.md`, 지시·대기·검사 명령은 `.hc/docs/lead.md`를 그대로 따르고, 여기에는 유지보수에서 달라지는 점만 적는다. Codex·Antigravity는 이 문서를 읽지 않아도 되게, 필요한 규칙은 Claude가 지시문에 옮겨 적는다(아래 5절).

## 1. 작업 크기 판단

- **작은 수정:** 파일 1~2개 안에서 끝나고 공유 계약·DB·인증을 건드리지 않는 수정은 Claude가 바로 처리한다. 2절의 현황 파악은 Claude가 직접 읽어서 하고, 3절의 기준선·회귀 확인은 생략하지 않는다.
- **그 밖의 작업:** 2절부터 순서대로 진행한다. 핵심 코드 교차 리뷰와 화면 변경의 브라우저 검증은 `lead.md` 1절 규칙을 유지한다.

## 2. 공통 절차 (수정·추가 모두)

1. **git 확인과 작업 브랜치.** 착수 전에 `git status`로 미커밋 변경이 없는지 보고, 있으면 사용자에게 알린다. 작업마다 브랜치를 만든다: 수정은 `fix/<요약>`, 추가는 `feat/<요약>`(영문 소문자·`-`). 브랜치 생성은 Claude가 한다(샌드박스 Codex는 `.git/`이 읽기 전용). commit·push는 지금처럼 사용자 승인 뒤에만 한다.
2. **현황 파악(읽기 전용).** 저장소 분석은 Codex에게 `담당 파일: 없음`으로 맡긴다. 보고에 받을 것:
   - 관련 파일과 호출부(바뀌면 영향받는 곳 포함)
   - 기존 테스트 위치, 테스트·빌드·실행 명령
   - 새 코드가 따를 **기존 예시 파일**(구조·이름·오류 형식의 본보기)
   - `AGENTS.md` 5절이 비어 있으면 채울 값(스택, 명령, 계약 파일 위치). 5절 반영은 Claude가 한다.
3. **기준선.** 수정 전에 기존 테스트·빌드·타입 검사를 한 번 돌려 결과를 남긴다(통과·실패 목록). 원래 실패하던 항목과 이번 작업으로 깨진 항목을 구분하기 위해서다. 현황 파악 지시에 함께 넣어도 된다.
4. **테스트가 없을 때.** 고칠 부분의 현재 동작을 고정하는 테스트(특성 테스트)를 먼저 최소한으로 만든 뒤 시작한다. 현재 동작이 버그여도 일단 그대로 기록하고, 고치는 단계에서 테스트를 바꾼다.
5. **최소 변경.** 요청받지 않은 리팩터링·포맷 정리·이름 변경·의존성 업그레이드는 하지 않는다. `담당 파일:`은 2단계에서 찾은 파일로 좁게 잡는다. 필요해 보이면 제안으로 보고한다.

## 3. 기능 수정 (버그 수정·동작 변경)

- **재현 먼저.** 버그는 재현 테스트를 먼저 만들어 **실패하는 것을 확인**한 뒤 고치고, 통과를 확인한다. 재현이 안 되면 고치지 않고 `blocked`로 보고한다.
- **변경 명세.** Claude가 "지금 동작 → 바뀔 동작"을 파일로 적고(`.hc/tasks/<작업ID>-spec.md` 등) 지시문에 경로를 넣는다.
- **계약·DB·인증이 바뀌면** `AGENTS.md`의 Claude 전용 영역 규칙을 따른다. 기본은 하위 호환 유지다. 호환이 깨지는 변경(응답 형식·필드 제거, 오류 코드 변경 등)은 사용자 승인을 받고, 호출부 갱신을 같이 지시한다.
- **화면이 바뀌면** Antigravity가 같은 흐름의 수정 전·후 스크린샷을 `.hc/qa/<작업ID>/`에 남기고, Claude가 직접 비교한다.

## 4. 기능 추가

- **기존 방식 따르기.** 2단계의 예시 파일과 같은 구조·이름 규칙·오류 형식으로 만든다. 새 라이브러리·새 패턴이 필요하면 먼저 제안하고 Claude가 정한다.
- **계약은 확장만.** 기존 계약에 항목을 덧붙이는 것이 기본이다. 기존 항목을 바꿔야 하면 3절 규칙을 따른다.
- **테스트.** 새 기능 테스트를 추가하고 기존 테스트 전체를 다시 돌려 기준선과 비교한다.
- **DB 마이그레이션.** 기존 데이터를 깨지 않게 쓰고, 되돌리는 방법(역마이그레이션 또는 복구 절차)을 함께 적는다. 파괴적 변경은 사용자 승인을 받는다.

## 5. 지시문에 옮겨 적을 것

Codex·Antigravity 지시문의 `목표:`·`검증:`에 해당하는 규칙을 적는다. 예:

```text
목표: <수정·추가 내용>. 기존 예시 파일 <경로>의 구조·이름·오류 형식을 따른다. 요청 밖의 리팩터링·포맷 변경·의존성 변경은 하지 않고 필요하면 제안으로 보고한다.
담당 파일: <좁은 범위>
계약: <변경 명세·계약 파일 경로>
검증: (수정) 재현 테스트 <파일>가 먼저 실패하는지 확인 → 수정 → 통과. 기존 테스트 전체 <명령>을 실행해 기준선(<보고 경로>)과 비교한다.
완료 조건: 새 테스트 통과, 기준선 대비 새로 깨진 테스트 없음
```

## 6. 보고서에 추가할 항목

Claude가 사용자에게 마무리 보고할 때, 그리고 하위 작업 보고를 받을 때 다음을 확인한다.

- 영향 범위(바뀐 파일과 영향받는 호출부)
- 기준선 대비 테스트 결과(새로 통과·새로 실패·원래 실패)
- 하위 호환 여부(깨지면 무엇이 어떻게)
- 되돌리는 방법(브랜치 이름, 마이그레이션 복구 절차)
