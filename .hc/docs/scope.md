# 파일 범위 검사와 수정 재지시 (Claude 전용)

`.hc/docs/lead.md` 3절의 요약을 자세히 적은 문서다. `claim`·`check`·`verify`·`release`·`status`·`--fix-of`를 쓰거나 종료 코드 6·7·8이 나왔을 때 읽는다.

Node 18+가 있으면 두 OS의 task 스크립트가 같은 `.hc/scope.mjs`를 실행한다. Node가 없으면 일반 전송은 경고 후 기존 방식으로 진행하지만 소유 검사·verified는 적용되지 않는다. `--fix-of`는 횟수 검사가 필요하므로 Node 없이는 거부한다.

`담당 파일:`은 한 줄에 쉼표로 구분한 프로젝트 상대 경로로 쓴다. 디렉터리는 끝에 `/`를 붙이고 읽기 전용 작업은 `없음`으로 쓴다. 설명은 경로 밖 괄호에만 두고, 경로에 공백·쉼표·괄호가 있거나 glob/제외 조건이 필요하면 파일 구성을 명시적으로 나눠 지시한다. `src/ (db.js 제외)`는 제외 조건을 기계 검사하지 못하므로 `src/server.js, test/`처럼 허용 파일을 열거한다. 해석 불가/누락은 경고와 검사 코드 8이며 검증 완료로 처리하지 않는다.

| 명령(task.sh 또는 task.ps1 뒤) | 의미 |
|---|---|
| `claim <ID> <경로>...` | 지휘자가 직접 수정할 파일 예약 |
| `status` | 예약·보고·검증 상태와 수정 회차 확인 |
| `check <ID>` | 기준선 이후 실제 파일 변경 분류 |
| `verify <ID> <검증 근거>` | 실파일·검사·테스트를 확인한 뒤 별도 verified 기록. 일반 작업은 done 보고 필요 |
| `release <ID> <사유>` | 중단/재할당 시 예약 해제. 대상이 더 쓰지 않는지 확인하고 실행 |

- `send`는 겹침이나 수정 한도 위반이면 6으로 거부한다. `check`/`verify`는 미소유 변경이면 7, 범위 해석 불가이면 8이다. 통합을 중단하고 원문/실파일을 확인한다. 통신 종료 코드(`wait` 0/2/3/4, `send` 5)와 OS 차이는 `lead.md` 3절 표를 따른다.
- 작업 기록은 `.hc/tasks/<ID>.scope.json`, 검사 근거는 `<ID>.check.txt`, 지휘자 검증은 `<ID>.verified.json`이다. 에이전트의 보고 상태는 계속 `done|failed|blocked`이며 verified를 보고에 쓰지 않는다. done/failed/blocked 보고만으로 예약을 자동 해제하지 않는다.
- 수정은 `send ... --fix-of <직전ID>`로 보내며 새 ID를 쓴다. 최초 작업 이후 이어지는 수정 지시는 **계열 전체 최대 3회**다. 원인 이름으로 세지 않고 같은 작업 계열로 센다. 4회째는 보내지 않고 실패 근거·시도·필요한 결정을 사용자에게 알린다. 보고 누락 `nudge` 최대 2회 및 Windows의 Enter 재시도와는 별개다.
- 수정 본문에는 이전 ID·보고/원문 경로, 실패한 명령·기대/실제 결과·로그/스크린샷, 이전 시도와 이번 수정 목표, 계약 변경 여부, 담당 범위, 재검증 명령을 넣는다. UI 오류가 백엔드/계약 원인이면 해당 소유자에게 재할당한다. 승인·로그인 등 사용자 조작이 필요한 blocked는 자동 재시도로 해결하지 않는다.
- 전송 실패·미제출·시간 초과는 작업이 실행되지 않았다는 증거가 아니다. 예약을 바로 해제하거나 같은 지시를 중복 전송하지 말고 화면·상태·기존 파일을 확인한다(macOS `PENDING=1` 복구는 `lead.md` 3절). 지시 후 대기 중인 작업의 범위를 바꾸려면 먼저 멈추고 확인한다.
- 수정 지시의 부모 예약은 전송 기록이 만들어진 뒤 내부 `sent` 단계에서만 해제한다. 전송 오류가 나면 부모와 pending 자식 예약을 보존한다. 전달 여부를 확인한 뒤 기존 예약과 같은 본문/범위로 재개하거나, 대상이 쓰지 않는 것을 확인하고 사유를 적어 해제한다. 재개는 기준선·수정 회차를 덮어쓰지 않는다. 옛 부모에서 새 분기를 만들거나 다른 범위로 같은 ID를 재사용할 수 없다.
- 공유 폴더에서는 변경자를 식별하지 못한다. 다른 작업의 허용 범위 안 변경은 정상 병렬 변경 후보이며 타 작업 파일 침범까지 검출하는 보장은 없다. 사용자/pi의 편집도 구분하지 못한다. 자동 되돌리기는 하지 않는다.
- 병렬 작업을 순서대로 검증할 때 먼저 완료한 작업의 변경도 인정하되, 검증/해제 때 저장한 파일 집합·해시와 현재 내용이 정확히 같아야 한다. 그 이후 변경은 새 활성 예약이나 재검증 없이 면제하지 않는다. verified 이후 담당 디렉터리의 파일 추가·삭제·내용 변경은 `status`에서 별표로 알린다. 이전 검증을 갱신하려면 새 ID로 검사 작업을 예약해 실제 검증한다.
- 실행 중 서버·watch가 계속 쓰는 파일(DB 파일·로그·빌드 출력·캐시 등. 예: SQLite의 `-wal`/`-shm`)도 프로젝트 파일 변경이다. 테스트 전에 해당 경로를 별도 `claim`하고 내용을 확인한다. 미예약 변경이 발견되면 원인을 확인하고 명시적으로 인수한 뒤 다시 검사한다. 관련 없는 변경을 숨기기 위해 소유 범위를 넓히지 않는다. 검사 중에도 계속 쓰이는 파일은 몇 번 다시 읽은 뒤 `unstable:` 표식으로 기록하고 검사를 계속한다. 표식은 내용 해시가 아니므로 문자열이 같아도 같은 내용으로 보지 않는다. 그래서 항상 변경으로 분류되고(예약 안 했으면 7), 그 파일이 담긴 verified는 `status`에서 항상 별표이며, 검증/해제된 작업의 해시로 면제되지 않는다. 내용을 고정해 검증하려면 쓰는 프로세스를 멈춘 뒤 다시 검사한다.
- `.git`, `node_modules`, `.hc/tasks`, `.hc/reports`, `.hc/qa`, `.hc/art`, `.omx`(Codex 플러그인 상태)는 스냅샷에서 제외된다. `check`·`verify`는 담당 항목이 `.hc/tasks`, `.hc/reports`, `.hc/qa`, `.hc/art`, `.omx` 또는 그 하위에 있으면 경고하며 종료 코드는 그대로다. 이 경로의 변경은 수동 확인해야 한다. 특히 QA/art 산출물은 보고 경로와 실제 파일을 직접 확인한다. 검사 완료 후 원복된 중간 변경도 탐지하지 못한다. 파일 변경에 따른 verified 표시는 실제 재검증을 대신하지 않는다.
- 감시 대상에 symlink/junction·하드 링크 또는 대소문자/Unicode 정규화 후 이름이 같은 별개 경로가 있으면 판정 불가(8)로 멈춘다. 디렉터리/파일 읽기 실패나 손상된 기록도 통과시키지 않는다. 내용 해시 검사는 권한·실행 비트 변경이나 검사 직후 외부 편집까지 고정하는 잠금이 아니다.

예: macOS `.hc/task.sh send <대상> fix-1 --fix-of original < 본문파일`, Windows `powershell -NoProfile -ExecutionPolicy Bypass -File .hc\task.ps1 send <대상> fix-1 <본문파일> --fix-of original`. 성공 보고를 받은 후 각각 `wait fix-1`, `check fix-1`, 실검증, `verify fix-1 "실행 명령 및 결과"` 순서로 수행한다.
